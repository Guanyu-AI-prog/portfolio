    技术洞察

    从实践中提炼的关键认知——不是"会用工具"，而是"理解边界"

    BM25 混合检索为什么能从 74% 拉到 98.7%？

    向量检索擅长语义匹配，但遇到精确关键词时反而模糊。BM25 的精确匹配恰好弥补短板。混合检索不是"加保险"，而是解决不同粒度的召回问题。

    小数据不该用 RAG

    数据量小（几万字以内），直接塞进 LLM 上下文窗口效果反而更好。RAG 的切块-检索-拼接会丢失上下文关联。RAG 是大数据场景的工具，小数据直接喂全文才是最优解。

    评测题可能存在"过拟合"

    60 道测试题 97.7% 零幻觉——但测试题基于知识库内容设计，等于"开卷考试"。评测的目的是暴露问题，不是证明自己厉害。

    三框架对比的真实发现

    Dify Agent 质量最高（97.3%）但响应慢（9s），LangChain RAG 最快（2.86s）但质量略低，LangChain Agent 兼顾。没有"最好的框架"，只有"最适合场景的框架"。

    纯 RAG 有天花板，突破靠"加一层"

    参数调到极限时，突破来自架构层面的改变——在 Chatflow 多加一个检索节点，召回率直接跳到八九十。

    检索 > 生成

    RAG 的核心不是模型，而是检索。检索不到 → 一定幻觉。Prompt 无法弥补检索缺陷。80% 的优化精力应该花在检索侧。

    数据质量决定上限

    结构化 > 非结构化，一致性 > 数量。文档编码、格式统一、Q&A 增强——这些"脏活"才是决定 RAG 质量的关键。

    工程 > 算法

    部署、存储、性能、环境配置、编码转换——这些工程问题占据了 60% 的时间。解决它们的能力才是落地 RAG 的关键。

    切分策略因场景而异

    Q&A 用小块（250字）、详情用大块（500字）、文学用父子层级、学术用双粒度。没有万能切分，只有最适合的切分。

    平衡而非最优化

    召回率 vs 准确率 vs 幻觉率是三角制衡。TopK=3~5、Score 阈值 0.6~0.7、严格 Prompt + 拒答机制。宁可不答，不可答错。
