从 2026.02 到 2026.06，完成从学习到三套系统落地的完整周期。代码实现借助 AI 辅助完成，但每一条检索策略的选择、每一个参数的调优、每一次架构的升级，都来自实际踩坑后的判断。

第一阶段：观望与学习（2月）

基础概念学习，了解 RAG 原理、向量检索、Embedding 模型等基础概念，观望各平台方案，为动手做准备。

第二阶段：动手搭建（3.20 起）

• 3.20 — 第一个 RAG：Cherry Studio 本地搭建，8GB 内存跑 bge-m3，CPU 99%，首次 RAG 对话成功。发现：基础搭建只是开始，检索生成才是灵魂。

• 3.25 — 4.2 — 平台探索期：5 个平台横向对比。腾讯云 ADP（幻觉严重）→ AnythingLLM（本地受限）→ LangChain（毛坯房）→ Dify（最终选择）。每个平台都教会了不同的东西。

• 4.2 — 文档编码之战。批量转换，PowerShell 乱码、Python 失败、VS Code 清空内容，最终用两步转换法解决。数据清洗是 RAG 的地基。

• 纯 RAG 的天花板 — 分块大小、overlap、相似度阈值反复调参，发现单靠参数调优无法突破。领悟：RAG 的核心矛盾是召回率 vs 准确率的平衡。

技术洞察

从实践中提炼的关键认知，不是"会用工具"，而是"理解边界"

💡 BM25 混合检索为什么能从 74% 拉到 98.7%？

向量检索擅长语义匹配（"便宜的套餐"→"低月租方案"），但遇到精确关键词（"实付69元"、"违约金30元"）时反而模糊。BM25 的精确关键词匹配恰好弥补了这个短板。两者不是替代关系，而是互补。关键认知：混合检索不是"加一个保险"，而是解决不同粒度的召回问题。

💡 小数据不该用 RAG

用 51 篇个人随笔做 RAG 实验时发现：数据量小（几万字以内），直接塞进 LLM 上下文窗口效果反而比 RAG 更好。RAG 的切块-检索-拼接过程会丢失上下文关联。关键认知：RAG 是大数据场景的工具，小数据直接喂全文才是最优解。

💡 评测题可能存在"过拟合"

60 道测试题得分率 97.7%、零幻觉——但测试题是基于知识库内容设计的，等于"开卷考试"。真正的验证需要线上真实用户提问。主动识别这个局限性，比追求高分更有价值。关键认知：评测的目的是暴露问题，不是证明自己厉害。

💡 三框架对比的真实发现

Dify Agent 质量最高（97.3%）但响应慢（9s），LangChain RAG 最快（2.86s）但质量略低（91.6%），LangChain Agent 兼顾（94.9% + 14.65s）。没有"最好的框架"，只有"最适合场景的框架"。关键认知：技术选型的核心是理解 trade-off，不是追新。

💡 纯 RAG 有天花板，突破靠"加一层"

花了三周在纯 RAG 上调参数，chunk_size、检索权重、prompt 改了个遍，召回率始终上不去。后来在 Chatflow 里多加了一个检索节点（无心之举），召回率直接跳到八九十。关键认知：当一个维度的优化到极限时，突破往往来自架构层面的改变，而不是参数微调。

💡 检索 > 生成

RAG 的核心不是模型，而是检索。检索不到 → 一定幻觉。Prompt 无法弥补检索缺陷。80% 的优化精力应该花在检索侧。

💡 数据质量决定上限

结构化 > 非结构化，一致性 > 数量。文档编码（ANSI→UTF-8）、格式统一、Q&A 增强，这些"脏活"才是决定 RAG 质量的关键。

💡 工程 > 算法

部署、存储、性能、环境配置、编码转换 —— 这些工程问题占据了 60% 的时间。解决它们的能力才是落地 RAG 的关键。

💡 切分策略因场景而异

Q&A 类用小块（250字）、详情类用大块（500字）、文学用父子层级、学术用双粒度。没有万能切分，只有最适合的切分。

💡 平衡而非最优化

召回率 vs 准确率 vs 幻觉率是三角制衡。TopK=3~5、Score 阈值 0.6~0.7、严格 Prompt + 拒答机制，接受"部分问题不回答"比"编造答案"好。

📊 RAG 评估标准

在四个月的实践中，总结出一套可量化的 RAG 质量评估框架：

  • 召回率 ≥ 80%
  • 准确率 ≥ 80%
  • 幻觉率 ≤ 20%
  • 完整性 ≥ 70%

评估方法论：问 10 个问题，2 个没召回可以接受，2 个答错可以接受，但编造不能接受。所以引入"可回答性判断"——生成前先判断知识库是否有答案，无答案直接拒答。宁可不答，不可答错。
